APIs drift.
Your code doesn't.

Register the third-party APIs you call and the pages you care about. When they change, you get Slack and email alerts, and API changes arrive as a GitHub PR that AI wrote and your tests verified.

Source → detect → fix → alert.

Nobody reads changelogs. Driftless reads the spec instead, and only speaks up when your code is actually affected.

01 · SOURCEAPI spec or web page

Pick what to watch. OpenAPI specs (JSON) are compared by endpoint; web pages are crawled and compared by text.

02 · DETECTChecked on a schedule

Checked one at a time on an interval. First check is the baseline; after that, only what changed. Empty responses never overwrite the baseline.

03 · FIXAI fixes the code

When an API changes, Claude patches the affected code and writes the PR. It must pass the range guard and your tests to become a PR.

04 · ALERTSlack · Email · GitHub PR

Changes go to Slack and email; code fixes arrive as GitHub PRs. A human merges.

1 · Diff the contract, not the changelog

Every field carries a stable identity in the spec. Same identity, new name means renamed. Identity gone means removed. New required field means callers must send it.

- "status":  { "canon": "status" }
+ "state":   { "canon": "status" }   → renamed
+ "idempotency_key": { "required": true,
    "x-migration-default": "str(uuid.uuid4())" }   → provider says how to fill it
2 · Find the exact call sites

The repo is parsed into functions. A function is affected only if it calls the changed endpoint with the same HTTP method. Everything else is left alone.

shop_client.py:17–19  create_charge()   POST /v1/charges
shop_client.py:22–24  charge_status()   GET  /v1/charges/{id}
shop_client.py:9–14   _call()           not affected
3 · AI patches, the guard checks the range

Claude reads the spec change and your code, then writes the patch and the PR description. The range guard compares old and new files and rejects any edit outside the affected functions, falling back to a rule-based patch.

-  r = _call("POST", "/v1/charges", {"amount": amount, ...})
+  r = _call("POST", "/v2/payments", {"idempotency_key": str(uuid.uuid4()), "amount": amount, ...})
-  return r["id"], r["status"]
+  return r["id"], r["state"]
4 · Prove it before anyone sees it

Your own tests run twice against the new API: on main (should fail, shows the break is real) and on the patched copy (must pass). Only then is a PR opened.

main     vs v2   FAILED (errors=2)  404 no such endpoint POST /v1/charges
patched  vs v2   OK
→ PR #1 "Adapt to Paylite API v2"

Built to be trusted with your codebase.

You give a tool access to your repo only if it is careful. These are the rules it follows.

What it can do
  • Read your repo and open branches and PRs. Never pushes to main.
  • Patch only affected functions. Out-of-range edits are rejected.
  • Open a PR only when tests pass against the new API version.
What it won't do
  • Never guesses when a field is removed with no replacement. It opens an issue.
  • Never merges. A human reviews every change.
  • Never trusts AI output blindly. Only the affected file is sent to the AI (Claude). Its patch must pass the range guard and your tests to become a PR. Without AI, a rule-based patch is used.
